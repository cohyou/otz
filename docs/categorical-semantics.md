# 圏論的意味論：状態族、実行事象、動的論理、貼り合わせ

> ステータス: 主要な構想は採用方針。一般的なインスタンス圏・スキーマ変換で成立する定理としては未証明の箇所がある。

## 1. 状態族と「領域」「時間」の分離

状態の集合を $W$、各状態 $w$ のスキーマ $C$ 上のインスタンスを $I_w$ とする。状態全体は Set 上のスライス圏を用いて

$$
\mathcal I:C\longrightarrow\mathbf{Set}/W
$$

すなわち

$$
\mathcal I\in[C,\mathbf{Set}/W]
\simeq\prod_{w\in W}[C,\mathbf{Set}]
$$

という族として表せる（固定の集合 $W$、Set 値の単純化したスキーマの場合）。

**設計原則**: `State` / `Step` を業務・領域スキーマへ加えない。変化は状態インデックス $W$ と実行事象側に置く。type-side 代数固定で属性を持つ場合、属性付きインスタンスの族を対応するスライストポス／ファイバーで扱うという案があるが、具体的な $H_A$ と圏の条件を確認する。

## 2. 各アクションの実行 span

アクション $a$ の実行可能な具体事象の集合を $E_a$ とする。典型的には事象が `(source state, query match, resulting state, optional execution witness)` を含む。

$$
W\xleftarrow{s_a}E_a\xrightarrow{t_a}W
$$

$E_a$ は単なる二項関係に潰さない。異なるクエリマッチが同じ前後状態を生成した場合も、実行証人として区別できる。

到達可能関係へ忘却すると

$$
R_a(w,w')\iff \exists e\in E_a:\ s_a(e)=w\land t_a(e)=w'
$$

を得る。`Rel` / Bool-valued profunctor への抽象化は後の検討項目。

## 3. 合成

アクション $a$、$b$ の逐次合成は中間状態を共有する実行事象の pullback による：

$$
E_{a;b}\simeq E_a\times_W E_b
=\{(e_a,e_b)\mid t_a(e_a)=s_b(e_b)\}
$$

実際に合成イベントを構成した結果がこの pullback と対応することを、有限ケースでテストする。複数ステップの結合性は自然な同型の意味で扱う。

`a \otimes b` のような「並行合成」は、独立の状態空間・操作なら直積で表せるが、共有更新対象がある場合は独立性・整合性・同期規則の定義が必要。普通の props だけで型付き DB インターフェースを十分表せるとは限らず、colored props やより一般の対称モノイダル圏を検討した。

## 4. 動的論理

部分対象 $G\hookrightarrow W$ を状態に関する性質とする。アクション span の始点・終点写像で引き戻した上で、存在／全称の随伴を使う：

$$
\langle a\rangle G=\exists_{s_a}(t_a^*G),
\qquad
[a]G=\forall_{s_a}(t_a^*G)
$$

`diamond` は到達できる実行が一つでも存在する、`box` はすべての実行結果で成立する、という方向性。事象が一つもない状態での box の扱い（空に対する全称）は明示する。

内部 DB の述語を $W$ 上の性質として読むとき、クエリ $Q$ の解集合族

$$
E_Q=\coprod_{w\in W}\operatorname{Hom}(F_Q,I_w)
\longrightarrow W
$$

を用いる。クエリの真偽だけでなくマッチ（証人）を持つことが Update に必要。

**未解決**: 静的 Doctrine 上の述語と、アクション span による動的モダリティがどのような基底変換・Beck–Chevalley 条件の下で整合するか。一般化を証明せずに「内部論理のまま完全統合した」とは扱わない。

## 5. 複数システムの静的・動的貼り合わせ

共有インターフェース $J$ を介してスキーマを接続する場面では

$$
S_1\longleftarrow J\longrightarrow S_2
$$

という **span**（共通インターフェースからの射の組）と、その pushout $S_1\amalg_J S_2$ を検討する。

各システムの状態は共通の $J$-部分に整合する場合に組にできるため、**制限先の一致**で pullback 的な組合せを行う。ここでスキーマ pushout からインスタンス側の（擬）pullback が一般に無条件で得られると主張しない。圏と同型／厳密一致の取り扱いに依存する。

動的貼り合わせではさらに

- 共有 ID と属性の値が実行前後で一致する条件
- 一方の更新が他方のスキーマ等式を破壊しない条件
- 共有事象を同期すべきか、独立に interleave するか
- 更新を合成したときの原子性
- 先に構成してから抽象化する場合と、抽象化した状態を合成する場合の整合性

を検証する必要がある。互いに独立なシステムの直積は、共有インターフェースが自明な特殊例として解釈できる。

## 6. 書換えの使い分け

- **Span**: 実行事象・遷移の意味論、逐次合成、マッチの関係づけ。
- **DPO/SqPO など**: 条件が整えば、エンティティ生成・削除を含む具体的書換えの記述候補。
- **共通インターフェースの span と Pushout**: スキーマの静的貼り合わせ候補。逆向きの cospan は別の合成問題で現れる。
- **Pullback**: 共有部分の一致やイベントの合成・同期条件の記述。

自然変換だけでは、既存エンティティの削除や型付き値の変更を常に意図どおり表現できるとは限らない。

## 7. 検証と並行性

当面のモデル検査は interleaving によって並行実行を直列化する。将来、アクションの因果関係・独立性・真の並行性が必要になれば event structure、Petri nets、open Petri nets などの意味論を比較する。

**システムを成立させる構造的制約** と **そのシステムについて検証したい性質** は分離する。例えばスキーマ等式に従うことと、到達可能な全状態で安全性が保たれることは別の要求である。
