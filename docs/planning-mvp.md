# MVP：固定スキーマ上の計画生成

> ステータス: 段階的実装の提案。ベンチマークの具体的スキーマと既存コードへの統合は未確定。

## 目的

有限インスタンス上で、`Query → Match → Patch → Validate → Apply` を実行し、初期状態からゴール条件を満たすアクション列を発見できる。

## 対象範囲

- 固定スキーマ、固定 type-side 代数
- 有限エンティティ、全域的な属性・外部キー
- 等式連言からなる frozen-instance クエリ
- 複数マッチの列挙（非単射の可能性も含む）
- Entity/Equation Patch: `Create`、`Delete`、`Set`
- Atomic な更新・整合性チェック
- `successors` による遅延列挙
- まず BFS による前向き探索
- ゴールを frozen query の解の非空性で判定
- プランと実行トレースの出力

## 最小の端から端までのシナリオ

1. 有限スキーマと初期インスタンスを用意する。
2. アクションの frozen query が複数マッチすることを検証する。
3. 一つのマッチから記号的 Patch を作る。
4. 属性／外部キーの値を置換し、整合した後続インスタンスを得る。
5. 無効な参照やスキーマ等式違反を含む Patch は拒否される。
6. 複数ステップの BFS でゴールが満たされる。
7. 得られたプランを初期状態から再実行し、各ステップ・最終ゴールを検証する。

## Blocks World の候補

Blocks World を最初の説明例とする。例えば `pickUp` / `putDown` / `stack` / `unstack` の一部を、等式条件と値更新で表現する。`clear`、`holding`、`on` 等の状態表現は **型と全域関数性を満たすように設計**する必要がある。

重要な点：PDDL の負条件や閉世界仮定を、単純な等式連言クエリにこっそり持ち込まない。MVP で必要な条件は、Bool 属性や明示的な状態エンティティなど、現行の等式クエリで検査可能な表現に変換する。補助属性の更新を忘れた場合には整合性テストで失敗させる。

## テストマトリクス

| レベル | ケース | 期待 |
| --- | --- | --- |
| Query | 等式条件が成立 | マッチを返す |
| Query | 等式条件が不成立 | 空集合 |
| Query | 複数の変数が同一実体にマッチ | 許す場合を明示し成功 |
| Query | RETURN 射影 | マッチと射影を区別 |
| Patch | 既存の属性値 `Set` | 値が置き換わる（追加等式による矛盾を作らない） |
| Patch | `Create` | 新規 ID・全域関数値が正しい |
| Patch | `Delete` | 削除・参照の処理が明確 |
| Patch | 同じ対象への競合 `Set` | 明示した規則に従い拒否／統合 |
| Validation | dangling reference | 拒否 |
| Validation | スキーマ等式違反 | 拒否 |
| Execution | 一つのアクションに複数マッチ | 各マッチから事象・後続状態を生成 |
| Planning | 1 ステップで達成可能 | 長さ 1 の有効なプラン |
| Planning | 複数ステップ必要 | 連続実行で最終状態がゴールを満たす |
| Planning | 到達不能 | 探索の終了条件に従う結果 |
| Planning | 同一状態へのループ | 重複検出が無限ループを防止 |

## 構成・拡張を分離

- **数学上の解集合**: 各状態の全マッチを与える。
- **実装上の列挙器**: 必要なマッチ／後続状態を遅延計算する。
- **探索**: BFS、ヒューリスティック、逆向き、SMT など交換可能。
- **最適化**: hash、同型判定、folding/subsumption、memoization は後から追加。

## 初回の Definition of Done

`Blocks World` の非自明な初期状態とゴールについて、コード実行で計画を得られ、生成した全ての遷移が再実行可能であり、ゴールを検証できる。加えて、既存コードとの対応と実装上の制約が記録される。
