# ADR-0006: LPO の優先順位では定数を最も小さくする

- 状態: 採用方針
- 日付: 2026-11-23（PR #12 で決定）

## Context

Knuth–Bendix 補完では、等式の向きを LPO（辞書式経路順序）で決める（PR #7〜#9）。LPO は演算子の優先順位を必要とする。

当初は `OperId` の大小（記号表に登録された順）を優先順位にしていた。インスタンスの要素（`e1`、`d2` などの 0 引数の記号）は、スキーマの関数（`wrk`、`mgr`）より後に登録されるので、優先順位が高くなる。その結果、`wrk(e2) = d2` が `d2 → wrk(e2)` の向きの規則になり、正規形が関数適用になっていた。等しさの判定は正しいが、`eval` の出力で e7 が `mgr!sec!wrk!e2` のような読めない形になっていた。

## Decision

- 優先順位を `(引数があるか, OperId)` の辞書式順序とする。**0 引数の記号（定数）は、すべての関数記号より小さい。**
- 同じ種類（定数同士、関数記号同士）の中では、`OperId`（宣言順）で比べる。
- `Int` / `Str` のリテラルは、従来どおり、すべての関数適用より小さい定数として扱う。値の異なるリテラル同士は比較できない。

## Consequences

- `wrk(e2) → d2` の向きになり、正規形ができるだけ生成元（インスタンスの要素）になる。評価の結果が要素になるという直感に合う。
- `OperId` ごとに引数の数は決まっているので、これは記号の上の全順序であり、LPO は簡約順序のまま。
- 定数同士の大小は宣言順で決まる。インスタンスに `e1 = e2` のような要素同士の等式があるとき、どちらが代表元（正規形）になるかは宣言順に依存する。等しさの判定には影響しないが、出力に現れる代表元は変わり得る。
- 順序付き補完（research-roadmap R1-a）に進む場合は、値の異なるリテラル同士にも順序を入れる必要がある。
